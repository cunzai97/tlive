# v1.5.3

本版本把原生 CardKit 流式设为默认。版本号顺 1.5.x 线继续：`v0.14.9` 之后的 `1.5.0 / 1.5.1 / 1.5.2` 是本不该出现的跳号，但既然已经按这个号发了三次、更新判定又按 semver 排，续到 `1.5.3` 才能让存量客户端正常收到提示。

## 主要变化

- 原生流式默认开启：`TL_FS_NATIVE_STREAMING` 的代码默认从 `false` 翻成 `true`。进度卡走 CardKit 实体更新（`cardElement.content` / `cardElement.patch`），实体操作的配额远高于编辑聊天消息，刷新密度不再被 230020 牵着走。需要 `cardkit:card:write`；client 没有 CardKit API 时发送层判定后退回普通整卡，与显式设 `false` 走同一条路径。
- 打字速率可配，默认 `delay` / 10ms / 4 字 ≈ 400 字符每秒：`TL_FS_NATIVE_PRINT_STRATEGY`、`TL_FS_NATIVE_PRINT_FREQ_MS`、`TL_FS_NATIVE_PRINT_STEP`（后两个 1..1000，非法值启动即报错）。之前实体里硬写 70/1/fast。主旋钮选 `print_step` 而不是 `print_frequency_ms`，是因为 tick 短到某个值以后客户端不再变快（看着有下限，但平台既不文档化也不校验：`freq=1`、`freq=100000`、`step=999999` 全部 `code=0`，只有 `step=0` 和非法 strategy 才报 `11311`）。调这两个数不用改代码，`scripts/live-feishu-print-probe.js` 可以量真机观感。
- 显示允许落后于模型：飞书按自己的时钟打印每次推送新增的后缀，所以"推送频率"与"打字速度"是两个互不相干的旋钮。页面统一 1 次每秒（原生专用的 400ms 节拍取消），`adaptiveFlush` 的 base=min=max 钉死它，体积/输出速度/延迟三档惩罚关掉，只允许限流阶梯把间隔拉长。常驻计时与工具行因此 1 秒一跳。
- 思考改整段轮替：300 token 一段、从左切、已经发布的边界不再随文字增长移动，全局保留最近两段、旧段整块下线。物理元素 ID 换成语义身份（新增 `progress-identity.ts`）—— 短思考长大后会并入工具组，按结构路径取的 ID 会在流式中途改名，客户端把它当新元素就整块重打。思考正文不再套代码围栏：围栏是给没有流式的路径准备的，每拍都在移动的尾栅栏只会让文本跳动。
- ⏳ 计时、计划板、write 实时块这类"只在运行中存在"的页脚不再被已确认页继承，分页后一律挪到最新那张卡：划过旧卡不会再看到停滞的计时或 📋 残块。
- 限流处理重做：连续拒绝按几何阶梯退避（2 秒起、15 秒封顶），一帧送达即清零。运行中的帧被拒后不再原地重放（此前固定 1 秒重试在实测回合里 14 次全被拒），改为标 `forceFlush` 交给下一拍；终态帧没有后继，所以等满窗口后必须发出去，上限 15 秒。连接丢失（没有 `retryAfter`）仍保留 1 秒原地重放，因为复用的正是 create 身份 —— 换节奏会多发一张卡。`nextDelay` 里的窗口检查提到 `hasMessage` / `waiting_permission` 两个短路之前，修掉首帧 create 被拒后每拍重撞同一个窗口的死循环。
- 修掉回退路径丢 2 秒编辑地板：`feishuStreaming` 的卡落在没有 CardKit API 的 client 上时按普通整卡 PATCH，此前只有 `feishuSnapshot` 受 `FEISHU_SNAPSHOT_PATCH_MIN_MS` 约束，于是 1 秒一次的整卡编辑直撞 230020。现在按"这张卡是否被原地编辑"判定，与是哪个 formatter 产出无关。
- 详情按钮被拒时打 `[feishu] detail <verb> rejected: <原因>`，覆盖 never-bound / expired-snapshot / foreign-source-message / other-topic / queue-full 与执行异常分类。授权检查一条都没有放宽。
- 死代码清理：`createStreamingSession` 链（含 `streaming.ts` 整文件 125 行）、`shouldSplitProgressMessage` 链（它每次调用都要完整跑一遍 prepareNativeCard + planFeishuCards 只为数页数）、`markdownPanel`、`splitByTableCount`、`chunkByParagraphBytes`、`history.ts`、`buttons.ts` 里被 format-home 取代的旧按钮组；`src/__tests__/e2e/harness.ts` 从 480 行减到 181 行；`knip.config.ts` 两条指向不存在路径的 entry 修正（此前 `main` / `shouldRunMain` 的假阳性来自这里），现在 `npx knip` 报 0 未使用导出与文件。

## 使用说明与保留行为

- 这条号是实测之后定的：本树最初按 `v0.15.3` 发过一次，两个远端都有那个标签和同名 release，内容除版本号与这份说明外完全一致。测下来 GitHub 的 `releases/latest` 取最近发布的那个 release（不是 semver 最大的那个），所以 `install.sh` 的默认取版当时确实指到了 0.15.3；但应用内检查与 `/upgrade` 在拿到 latest 之后还要过一次按 semver 的 `compareVersions`，装着 1.5.2 的机器对任何 0.15.x 都算出"没有更新"、只会回"已是最新 1.5.2"，存量客户端永久收不到提示。号续到 1.5.3 之后两条路都正常：1.5.3 > 1.5.2，存量会被提示，新装也拿到同一个版本。`v0.15.3` 那个号已经收回 —— 两个远端的标签、GitHub Release 与 `release/0.15.3` 分支都删了；删时它的资产下载数是 3 次且全部来自我自己的取包验证（fork 为 0 次），包内容除版本号与这份说明外与 v1.5.3 同树，`e7dec7e` 与 `c07790e` 两个提交仍留在 v1.5.3 的历史里，所以没有任何提交或资产是别人唯一能拿到的东西。
- 一轮结束会关流（`streaming_mode=false`），而飞书关流时直接显示最终全文、不再动画，所以收尾瞬间还没打完的尾巴会一次性上屏。要做到"结束后慢慢追上"只能延迟关流，而 CardKit 没有读回接口、无法知道客户端实际打到第几个字，只能按"上次推送时刻 + 速率"估算，这套状态机没写。
- 定高滚动思考窗（`max_height`）真机两轮探针确认客户端确实 honored 它（探针与结论留在 `docs/design/card-native-streaming.md`），但观感上"会被吸附到最底下"，因此本版本未实现。
- 子代理进度卡仍走普通整卡 PATCH、仍吃 2 秒地板，所以仍可能报 230020；并行四张实体是否撞租户级 50 次每秒也未实测。
- CardKit 没有实体内容读取接口，`card.create` 也没有请求 UUID 字段（创建响应丢失可能留下一个未发送的孤立实体），所以本版本的验证是接口响应级加真机观感，不是远端内容读回。
- 协议没有变化：不新增事件种类，`REMOTE_PROTOCOL_VERSION` 仍为 1。改动集中在 `src/server/**` 与 `src/shared/**`，client 侧只删了没人用的导出，因此只换桥就生效，不需要一起换 client。
- 本次发布不合入 main，只发 `release/1.5.3` 分支与 `v1.5.3` 标签（与前三次一致）。`npm run check` 全绿：97 个测试文件 / 1029 项，typecheck 与 biome 无告警。
